- The viewer app should be hostable in a self contained docker container. People wishing to use the tool should be able to self host it and configure it as they need.
- Generation of the reports should be done with a headless CLI tool. Either provided the path to some file that represents the tool specific output or piped in on stdin. It should then upload the processed report data to a configured storage.
- The types of reports that can be generated / viewed should be extendable with plugins. While MVP should support Pulumi diffs, future tools like test results, configuration summaries etc could be supported and/or enabled by users hosting the tool.
- Plugins should be represented with node packages.
- Plugins can be "viewer", "reporter" or "storage" plugins so that CI/CD workflows don't need to download code used only for displaying and rendering the report.
- Report data should be able to be stored/retrieved from an extendable list of sources, e.g. S3 bucket, Github Artifact, user uploaded JSON file etc. Ideally someone using CI/CD actions should be able to generate the report, put the report file somewhere and then provide developers links to the viewer app that pre-load the report file, or in the case of user uploaded reports, they can drag and drop it into the viewer. Setups should be able to support multiple types of storage so the links used to view the reports can include information about the storage as needed. Potentially as "named" connections.
- Reports should record where they came from: the commit, branch, tags and remotes of the checkout, and the CI run and pull request when there is one, captured at generation time. The CLI should collect this itself so that every report carries the same facts regardless of which reporter produced it, and a user should be able to add their own entries or turn collection off. Plugins should be able to read it through a stable interface, and it should be extendable with new facts in future versions without breaking readers of older reports. The viewer app itself displays it, since it is the same for every report kind.
- The viewer app should be stateless, excepting the configuration for the enabled viewer and storage plugins. It should not need to be involved in generation and storage of reports other than the CLI tool knowing the hostname of the instance and the storage to use.
